# REA of the macOS t8110 DART driver on this Mac: fault handling, ADT options, USB instances (2026-10-18)

Offline static analysis (REA/Ghidra) of this Mac's own macOS 26.6.2 (25G83) binaries, done to answer the open
questions of the boot040 audit (`README.md`, D1-D7). **Behaviours only**: register offsets, bit meanings,
sequences and which ADT keys change what, each with binary, function, address, evidence and confidence.
Nothing from the decompiler is in this file; pseudocode and extracted bytes stay under the ignored
`build/macos-drivers/` tree. Nothing ran on the M5. Labels: **Confirmed / Likely / Hypothesis / Unknown**
("Confirmed" = read directly from the binaries' control flow, not from hardware).

## Summary of the answers

1. **Fault interrupt.** The register layout is selected by the DART version in PARAMS3 (offset 0x08) bits 15:0.
   Versions below 2.2 use the layout Linux knows (ERROR 0x100 with the flag in bit 31, ERROR_MASK 0x104,
   ERROR_ADDRESS 0x170/0x174, secondary bitmap 0x1c0). **Versions 2.2 and later use a different layout**: a
   per-stream pending bitmap at 0x4000 (write-1-to-clear), a 64-byte error block per stream at 0x8000 + 0x40·SID,
   and the error mask at 0x4060; 0x100/0x104/0x1c0 are never touched for them. Acknowledgement is a write-back of
   the pending bits (pre-2.2: the code bits to 0x100 and the 0x1c0 bitmap; 2.2+: the 0x4000 words), followed by a
   TLB "flush-unlock" command when register 0x210 bit 1 is set. Which version the t6050 has is **Unknown** (boot040
   prints it); if it is 2.2 or later, Linux can neither see nor clear a fault, which is exactly the attempt-21 storm.
2. **dart-options** (USB 39 = bits 0,1,2,5): bit 1 = access-region protection present, bit 2 = do not request the
   TTBR/TCR lock, bit 3 = PIO windows, bit 4 = dynamic stream-id assignment (PCIe), bit 5 = forced on by the t8110
   driver, bit 6 = persistent mappings (display); bit 0 Unknown. None selects a register layout or TLB policy.
3. **TLB policy and address space.** `flush-by-dva` = 0 means every TLB invalidation is "flush this stream"
   (TLB_CMD op 1), the same op Linux uses. `avoid-tlbi-in-map` only skips the flush when a map fills previously
   invalid entries; unmap always flushes. `remap` is a **stream-id remap** (pairs of bytes; 256 = stream 0 → stream 1),
   programmed in TCR bits 11:8 with bit 7, not an address remap. The 1 TiB window comes from `vm-base` with ordinary
   **3-level** tables (TCR bit 3 clear): the SPTM requires every Gen2 DART window to lie in [2^40, 2^42) and sets
   4-level only when a stream's window ends above 2^40 + 2^36. On versions 2.2 and later every TLB command carries
   bit 15 and is followed by a write of 0 to register 0x600 when PARAMS2 bit 4 is set; Linux does neither.
4. **USB instances.** macOS has no per-instance programming: one DART object owns both register instances
   (DART/0 "LLT", DART/1 "BLK") with one stream-id space, and every stream write (TCR, TTBR, enable/disable, TLB
   command, fault clear, mask) goes to **every instance**. The device-mode driver (`AppleT8142USBXDCI`) and the host
   driver share `mapper-usb0` (reg 1) → stream 1, so stream 1 is valid on instance 0 and instance 1, and stream 0 is
   remapped to stream 1 on both. Which traffic class carries stream 0 or passes instance 0 is not visible in
   software (Unknown); Asahi's wiring (instance 0 ↔ stream 0, instance 1 ↔ stream 1) is consistent with it.

Fix candidates (`README.md`): **A supported**, **B supported if PARAMS3 reports version ≥ 2.2** (and then larger than
a match-table entry), **C supported as a defensive mirror of macOS** (window at 1 TiB or 32-bit as m1n1), **D ruled
out as a correctness issue** (Linux flushes are a superset), with one open item (bit 15 / 0x600 on 2.2+). Details in
§9.

## 6. TLB commands

| # | Finding | Confidence |
|---|---|---|
| T1 | TLB_CMD at 0x80: bits 7:0 stream id, bits 10:8 operation, bit 31 busy. ## 9. Fix candidates (`README.md`) in the light of these findings

* **A, two-DART wiring: supported.** macOS treats instance 0 as a full, identically programmed DART instance on the
  same interrupt line; with our DT instance 0 is never reset, never programmed and never acknowledged, and stream 0
  (which macOS remaps to stream 1) is not configured anywhere. Asahi's `<dart0 0>, <dart1 1>` covers the hardware's
  stream ids per instance; giving each instance both streams (`<dart0 0>, <dart0 1>, <dart1 0>, <dart1 1>`) mirrors
  macOS's remap exactly and costs nothing. Decide on boot040's instance-0 snapshot as planned.
* **B, error layout: supported if boot040's probe line reports PARAMS3 version ≥ 2.2** (bits 15:0 ≥ 0x202). Then the
  change is larger than a match-table entry: read the pending bitmap at 0x4000 + 4·k, the per-stream block at
  0x8000 + 0x40·SID (summary, address at +0x08/+0x0c), acknowledge by writing the bitmap words back, unmask by
  writing 0 to 0x4060 at reset, clear 0x704 (or 0x4204 from 2.4) with all-ones, and (from the SPTM's behaviour, need
  Unknown) set bit 15 in TLB commands and write 0 to 0x600 when PARAMS2 bit 4 is set. If the version is below 2.2,
  B is ruled out: Linux's layout and acknowledgement match macOS's.
* **C, IOVA range: supported as a defensive mirror of macOS, not shown to be the cause.** `apple,dma-range =
  <0x100 0x00004000 0x0 0xffff0000>` is macOS's window (Linux would still select 4-level tables for it, which macOS
  does not use there); a 32-bit window is what m1n1 proved. Linux's current top-down allocation near 2^42 with
  4-level tables is used by no other software on this hardware.
* **D, TLB policy: ruled out as a correctness issue.** macOS flushes the stream on every unmap and on overwriting maps;
  Linux's per-map and per-unmap flushes are a superset and `avoid-tlbi-in-map` is a pure optimisation. Open: bit 15
  and the 0x600 write on versions ≥ 2.2 (T6), which Linux omits.
