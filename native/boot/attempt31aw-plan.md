actionable source defect. In each mode it passed 11 unchanged published methods
and an equivalent genuine retained-candidate method; the absent-kit published

Those counts remain distinct from M5's 12 unchanged producer methods per mode.

The actual [31AU result](attempt31au-recovery-2026-11-15-result.md) is still a

remained disabled. Exact boot021 restoration and Macintosh HD desktop/default
return are human-confirmed with the recorded transcript limits. No repeated
policy check or historical private-state read is needed.

## Implemented integration

The new `tools/boot-object31aw-native/` derives a separate helper, profile, scratch
and state namespace. It integrates the reviewed bounded buffer path as the
selected compressed object's recognition authority. Strict complete framing,
declared output counts, the extra destination byte, input/output bounds,
keybag refusal and exact known size plus SHA-256 remain mandatory. The original
core/header, AU controller, AV proposal and all 190 frozen AU inputs are retained.

The same existing selected-file read now supplies finite decode subreasons:
allocation failure, zero decode return or output-count disagreement. No alternate
Preboot scan, second selected-file read, decryption or guessed identity is added.
The full transaction still requires exact candidate identity **and enabled lab
CTRR**, Original Full and its private/semantic preservation, target/role binding,
durable one-shot state and owned mount cleanup.

Bounded synthetic positive/negative codec controls run before installation can
reach target/mount/state/writer operations. A standalone `--codec-capability`
dispatch runs only those controls, with no live collector. Failed controls block
installation. They do not prevent candidate-independent raw boot021 restoration:
that path retains its separate exact-artifact and preservation guards.

Namespace-normalized source comparisons preserve the writer, terminal, mount,
target, state/durability and cleanup bodies. The only transaction-flow addition
is the reversible codec preflight. New observer relations keep capability and
decoder results consistent; a display validation is not a successful transaction.

The integration also exposed an old display defect: the frozen JSON parser
rejects negative numbers, although valid pre-writer refusals contain
`writer_exit=-1`. An AW-only reversible parser change admits exactly canonical
`-1`; the result observer still permits it only for no-writer outcomes. Profile
byte counts/deadlines retain their unsigned exactness checks. Malformed negative
forms and negative profile values are exercised as deliberate refusals.

Final root validation passed **52 controller methods normally and 52 under
ASan/UBSan**, with genuine own artifacts, synthetic OS/writer backends and zero
skips. Independent review passed five decisive methods plus the pure capability
dispatch and checked all safety/source bindings. The optional legacy-reference
path separately passed its enabled-boot021 check and explicitly skipped only
the missing legacy control. Detailed attribution and source pins are recorded
in the [offline receipt](attempt31aw-offline-2026-11-15.json).

This remains an offline integration. Its maximum temporary decoded output is
160 MiB plus one byte, plus library scratch. Real Recovery memory/runtime behavior
and the historical selected carrier's exact cause remain unqualified. A successful
controlled decode does not establish firmware entry, physical SMP or performance.

## What REA resolved, and what it did not

The [receiver investigation](../../research/attempt31aw-ctrr-2026-11-15.md) crosses
the previously unknown kernel boundary: the checked BootPolicy user client
validates admission, maps the request, copies it to SEP-visible storage and sends
it through `sep-endpoint,pnon`. It does not edit SIP2/Kernel CTRR on that host path.
Three REA queries and independent original/derivative/LLVM comparisons support
the bounded result. The retained kernel's version is explicitly separated from
the unqualified actual Recovery/SEP runtime.

The policy transformation is in the matching pnon application handler. Its
mode-byte semantics have not been qualified. This is a precise remaining
boundary, not evidence that Apple must issue a CPU fix. No protected firmware
decryption, endpoint call, security bypass or new policy writer is introduced.

## Most promising future experiment: a deliberate lab baseline

Apple documents Permissive policy reconstruction separately from the CTRR-disable
option. Omitting that downgrade during reconstruction could remove the inherited
disabled setting without relying on Mach-O enrollment to clear it. The
[public-contract record](../../research/attempt31aw-public-contract-2026-11-15.md)
distinguishes this supported mechanism from an enable-only operation and from
Aura's reported automatic-enable behavior.

**This phase is not implemented or authorized in AW.** It needs its own controller
contract and review; issuing the command before the existing controller would
lose the very before/after binding we need. A useful design has two baselines:

1. Bind Original's exact private/semantic invariants **before** any lab reset and
   require them throughout. Retain the old lab observation as history. Confirm
   there is no auxiliary trust or unknown security option whose loss cannot be
   restored through supported means.
2. Use one exact lab-only policy reconstruction, with an explicit approved list
   of lab security changes. Requalify target, owner/paired Recovery, Permissive
   state and enabled CTRR immediately. A missing or still-disabled result stops
   before candidate installation. No intermediate policy is bootable evidence.
3. Bind a fresh post-reconstruction lab baseline; do not falsely compare newly
   issued opaque lab commitments with the old ones. Permit a cleared selected
   reference only in this nonbootable intermediate phase. Require exact candidate
   identity, enabled CTRR and Original preservation before any candidate boot.
4. Keep independent raw boot021 restoration and Original default/desktop return.
   It can restore the exact boot021 payload and declared lab security behavior;
   it cannot promise recovery of old lab policy bytes, signatures or opaque
   commitments after reissuance. That distinction must be explicit in owner
   authorization and in the rollback result.

The failure path needs the same care: reset may succeed while readback fails or
the new lab baseline is refused. Rescue must still be available **before** a
post-reset baseline exists. The old AU restore would reject changed lab metadata;
it cannot be advertised as this experiment's rescue. Qualify a separate bounded
reset-failure restore against the pre-reset Original/target/owner invariants and
explicit lab-reissuance contract, or prepare an independently reviewed manual
Recovery rescue. A happy-path fresh-baseline test does not establish that rescue.

A future combined window could qualify the actual Recovery codec/runtime, test
this one policy transition, conditionally install and observe entry, then restore.
It would answer whether an enabled baseline works, rather than repeating the
known failed disabled-baseline transition. Implement and review that state
machine before proposing the window. AW contains no reconstruction writer and
does not supply that authorization.
