# boot039: a bulk-only USB log port, with the dwc3 state on screen, prepared offline

2026-10-16, M5 side session. **Native boot039 NOT RUN.** It builds on
`boot038-control-channel-2026-10-16.md` and the attempt-18 result
(`stage-b-2026-10-16-attempt18-result.md`). Labels: Confirmed / Likely / Hypothesis /
Unknown. "Confirmed" here means confirmed by source, VM or package check, never on the
M5's hardware.

## Summary

* **One variable for attempt 18's question:** boot039 replaces boot038's CDC-ACM +
  CDC-ECM with **one bulk-only function**, the kernel's generic serial function `gser`.
  It has one vendor-class (`0xff`) interface, one bulk-IN and one bulk-OUT endpoint, **no
  interrupt endpoint** and no class requests. The kernel-log streamer is unchanged in
  substance: it only writes to `/dev/ttyGS<n>`.
* **The screen names a wedge without any USB link:** debugfs is mounted, and every
  heartbeat's `[ctl]` line now carries, per dwc3 controller, the link state, SOF frame,
  pending event bytes, interrupt count, the last EP0 OUT/IN command, and each enabled
  endpoint's type and TRB ring state. It also carries the log stream's counters. A
  one-time line per controller gives its endpoint count and TX FIFO sizes.
* **Image, kernel config, Stage-B DT, m1n1 and the generic files are byte-identical to
  boot036.** The Stage-B initramfs differs from boot036's **in `/init` only**. Both are
  packager-enforced.
* **bcdDevice `0x0139`, not `0x003a`:** configfs accepts only BCD. The VM self-test
  caught `0x003a` being refused (`EINVAL`, the gadget fell back to the kernel default
  `0x0701`). boot036 used `0x0036`, boot038 `0x0038`, and the RAM root uses `0x0039`.
* **Package** `ilinux-j716c-boot039.tar.gz`: 18,915,359 bytes, SHA-256
  `b85c8d45552f21de475e46009599a06b3d723b44e66cbc0087ff5fdf00b57d51`; SHA256SUMS digest
  `883464897e2e3233a96ed27c8af0e50d73474edf107f89ec9c40ab84e3684df5`. **Published** as the
  prerelease `native-j716c-boot039` (tag on `713989c`); GitHub's asset digest and a fresh
  download equal the local archive. The handoff records in `native/boot/`
  (`package-manifest.json`, `intake-manifest-sha256.txt`, `archive-sha256.txt`) point at
  it: attempt 21.
* **VM:** job 041 PASS (kernel facts, status-line fixture plain and under ASan+UBSan,
  clean `-Wall -Wextra` build). `selftest/run-vz.sh` PASS: liveness 8/8 present + 4/4
  absent, self-test 16/16 present + 4/4 absent. The host side read **1,926 kernel-log lines
  over the bulk-IN endpoint**; a probe the host wrote was not echoed.
* **M1 side:** `tools/m1n1-client/bulk-log-reader-brief.md` specifies a read-only reader
  that uses only the macOS SDK (IOUSBHost). It opens the vendor interface, reads bulk-IN
  to a file and never writes to the device. Not built.

## What boot039 changes

Only `/init` (`kernel/experiments/usb-gadget/init.c`, packaged as `diag-init.c`):

| | boot036 | boot038 | **boot039** |
|---|---|---|---|
| Functions per gadget | CDC-EEM | CDC-ACM + CDC-ECM | **`gser.GS0`: class `0xff`, bulk IN + bulk OUT** |
| Interrupt endpoints | none | two (one per function) | **none** |
| Interfaces / IN endpoints used | 1 / ep1in | 4 / ep1in-ep4in | **1 / ep1in** |
| Class requests | EEM: none | ACM's and ECM's | **none** (`f_serial.c` has no setup handler) |
| `bcdDevice` | `0x0036` | `0x0038` | **`0x0139`** |
| Network | `usb0`, IPv6 link-local, SSH | ECM `usb0`, SSH | **none**; dropbear still runs, on loopback only |
| Kernel log to the M1 | — | over ACM, read by macOS's ACM driver | **over bulk IN, read by the M1's own user-space tool** |
| Status line | UDC state, link, counters | the same | **UDC state, log counters, dwc3 state** (below) |

Smaller changes, all in `/init`:

* The streamer sets its tty raw (`cfmakeraw`), so nothing a host sends is echoed and
  lines end in exactly one CR LF. boot038 sent CR CR LF.
* The streamer counts records and bytes and samples the queued bytes (`TIOCOUTQ`), in
  memory shared with `/init`.
* debugfs is mounted at `/sys/kernel/debug`.

## Why `gser` (Confirmed from the boot036 tree, `selftest/check_kernel_facts.py`)

* `CONFIG_USB_CONFIGFS_SERIAL=y` and `USB_F_SERIAL=y` are already in boot036's config,
  so the Image needs no change.
* `f_serial.c`: one interface, `bInterfaceClass = USB_CLASS_VENDOR_SPEC`, two endpoints,
  both `USB_ENDPOINT_XFER_BULK`. There is no interrupt endpoint, and no `setup` handler,
  so no class request is answered or needed. `gser_set_alt` only enables the two bulk
  endpoints and calls `gserial_connect`, which queues the bulk-OUT reads and starts
  bulk-IN with the buffered log. It sends no notification.
* On the host side, Linux's generic usb-serial driver reads such an interface once it is
  given the VID:PID (`new_id`). The VM self-test uses that. macOS has no driver for it,
  so the M1 reads it from user space.

## What a clean result would and would not isolate

boot039 removes the interrupt endpoints. It also removes everything else that only
boot038 had: the CDC class descriptors and IADs, the ACM/ECM class requests, the second
function, and the use of IN endpoints 2–4 (each IN endpoint uses the TX FIFO of its
number, `DWC3_DEPCFG_FIFO_NUMBER`). Its endpoint use is attempt 17's (ep1in/ep1out).
New against attempt 17: the interface class is `0xff`, not CDC, which may change which
macOS composite driver configures the device (Unknown), and bulk-IN data really flows.
So:

* if the log arrives and no EP0 timeout appears, the wedge needs something only ACM/ECM
  had. **The interrupt endpoint is the leading candidate (Likely), not proven alone.**
  The TX FIFO line (below) can weaken or support the FIFO alternative from the same
  video;
* if the timeouts return, the interrupt endpoint was not the cause (Confirmed for that
  case), and the dwc3 line on the screen says where the core stands.

## The status line (new)

Example from the fixture test, port 1 streaming:

```
[ctl] port1 configured log 1796L 151234B q0 dwc3 On f4660 ev0 irq412 ep0 o:start i:start 1out bulk h16 d0 1in bulk h0 d37
[ctl] port1 dwc3: core 0x5533330a, 8 endpoints (4 IN), MDWIDTH 64; TX FIFO words 0:66 1:388 2:388 3:0; RX FIFO words 773
```

| Field | Source | Meaning |
|---|---|---|
| `configured` | `/sys/class/udc/<UDC>/state` | gadget state, as before |
| `log 1796L 151234B q0` | streamer counters | records and bytes accepted by the M5's tty; bytes still queued in its 8 KiB FIFO. No host reading: B stops near 16 KiB, `q8192`. Host reading: B grows, q near 0. |
| `On` | `link_state` | `dwc3_gadget_hs_link_string`: On, Sleep, Suspend, Disconnected, Early Suspend, Recovery, Reset, Resume |
| `f4660` | regdump DSTS[16:3] | (micro)frame number of the last SOF. If it changes between heartbeats, the host is sending SOFs. |
| `ev0` | regdump GEVNTCOUNT(0) | event bytes the driver has not handled; normally 0 |
| `STOPPED` `HALTED` `BUSERR` `CSR-TIMEOUT` `EVBUSY` | DCTL.RUN_STOP clear, DSTS.DEVCTRLHLT, GSTS bits 4/5, GEVNTCOUNT bit 31 | printed only when present |
| `irq412` | `/sys/kernel/irq/<n>/per_cpu_count` for the `dwc3` action whose hwirq (bits 15:0) is the UDC's DT interrupt | dwc3 interrupts taken; port 1 = AIC 0x58b, 2 = 0x5ab, 3 = 0x5cb |
| `ep0 o:start i:start` | regdump DEPCMD(0), DEPCMD(1) | last command issued on EP0 OUT / IN; `*` = still active (CMDACT), `!N` = nonzero command status |
| `1in bulk h0 d37` | DALEPENA, `ep1in/transfer_type`, `ep1in/trb_ring` | every enabled endpoint above EP0: type (an interrupt endpoint would print `INTERRUPT`), TRBs owned by hardware, dequeue index; `c:` shows its DEPCMD only when active or failed |
| one-time line | regdump GSNPSID, GHWPARAMS0/3, GTXFIFOSIZ(n), GRXFIFOSIZ(0) | core id, endpoint counts, MDWIDTH and FIFO depths in MDWIDTH words |

**Confirmed (source):** these four kinds of file are what this tree creates
(`drivers/usb/dwc3/debugfs.c`). `link_state` reads GSTS and DSTS; `regdump` only reads;
`transfer_type` and `trb_ring` read driver memory. The other per-endpoint files
(`*_fifo_size`, `*_queue`), `GDBGEPINFO` and `lsp_dump` **write** a debug select register
(GDBGFIFOSPACE, GDBGLSPMUX) when read, so `/init` never reads them. dwc3 runtime PM is
forbidden at probe (`pm_runtime_forbid`), so the reads resume nothing.

**Confirmed (source): there is no `ep0state` file.** The driver's EP0 state machine
(`dwc->ep0state`) shows only in tracepoints, and `CONFIG_FTRACE` is off. The line gives
EP0's last commands, the pending events and the interrupt count instead.

**Likely:** the reads are safe on the real cores. Every regdump offset lies inside the
core's mapped window (DT `reg` size `0xcd00`, highest offset `0xcc10`), and the dwc3
driver reads most of these registers itself. Still, they have **not been read on this
hardware**. The first read comes at heartbeat 000 (≈ 3.5 s), before the M1 enumerates.
A fault there would show at once, before any USB traffic.

**Confirmed (VM fixture):** the parsing. A child process does the reading and prints the
line. `/init` waits at most 2 s and otherwise prints the line without the dwc3 part, plus
`[ctl] dwc3 status reader pid N did not finish in 2 s`. So a blocked debugfs read, or a
fault in the parser, costs a status line and never the heartbeat.
