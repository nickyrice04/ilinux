# 31AP typed-policy Recovery diagnostic

This original wrapper reuses the exact successful 31AM conditional read-only
Preboot engine and its one-paste shell flow. The helper adds the REA-qualified
31AO policy grammar and private v3 comparisons. Desktop syntax success does not
establish Recovery pairing, security, selected-object or admission success.

The package retains every one of the 111 old source pins and all 14 AO source
pins. Its new inventory binds the native build proof, canonical public profile,
two-file delivery, renderer and M1 handoff. Existing kits, profiles, receipts,
candidate, boot objects and consumed transaction state remain untouched.

The new kit contains only `ilinux31aj-reader` and `profile.json`. Its eventual
separate staging destination is the lab Data directory
`Users/Shared/iLinuxBoot/31ap-diagnostic`. Preparing or checking a page performs
no staging, server startup, mount, policy query or boot operation.

```sh
python3 -I tools/recovery31ap/package.py --prepare --kit build/ilinux-31ap-diagnostic --output build/31ap-diagnostic-page
python3 -I tools/recovery31ap/package.py --page build/31ap-diagnostic-page/recovery.html --check-only
```

Default and `--help` are inert. `--stage` is a separate future authorized lab
Data copy; page service is a separate future explicit invocation. Neither was
performed during offline preparation. No install, restoration, security-write
or native-boot mode exists in this controller.

The page contains one complete box. On a later authorized Recovery visit, copy
the whole box, quit the browser, open Utilities Terminal and paste once. The
unchanged native CLI conditionally prepares only its own verified read-only
Preboot mount, runs the guarded diagnostic, and attempts only its own cleanup.
Its existing strict validator precedes any finite result display. Refusal or
uncertain cleanup remains a stop, without retry or improvised mount commands.

Even a passing diagnostic authorizes no installation or Linux boot. A later
transaction would require review of the actual Recovery result and an explicit
lab-only scope; it must not reuse or reset old consumed state blindly.

Focused offline controls:

```sh
python3 -I tools/recovery31ap/test_package.py
python3 -I tools/recovery31ap/test_render.py
```

These controls verify source retention, exact build/profile bindings, immutable
dependencies, kit/schema-only shell changes, the rendered scratch basename
against the frozen native predicate, one-box HTML and Bash syntax. The original
`ilinux31am.` scratch prefix is retained because the fixed engine requires it;
`mktemp` still creates a fresh directory and reuses no previous state. Inherited
31AM engine/shell evidence is reused; these tests do not claim physical Recovery,
mount cleanup, native Linux, SMP, acceleration or performance success.
